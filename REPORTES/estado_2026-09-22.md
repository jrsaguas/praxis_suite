## Estado ejecutivo

La arquitectura de endurecimiento, auditoría, perfiles, experiencia y selección está bastante avanzada, pero **todavía no debe integrarse a main**. El punto principal pendiente es comprobar y cerrar la integración efectiva del runtime con el servidor y ejecutar la batería real en CI.

## Confirmado en código

- Seguridad de rutas, nombres y payloads.
- Configuración centralizada del servidor y CORS local.
- Verificación CAS con estados explícitos.
- Contratos de verificación/pipeline.
- Orquestador answer → review → CAS/RAG → evaluación → retry.
- Grafo de agentes con dependencias y selección de modelo.
- `final_auditor` como etapa terminal.
- `experience_evaluator` posterior al auditor.
- Perfil multidimensional 0–100.
- Selección de experiencia por perfil y relevancia.
- Persistencia de experiencias con estados de reutilización.
- Separación candidate/accepted/rejected.
- Promotion Gate restringido a evidencia aceptada.
- Trazabilidad operacional observable.
- Manifiesto de artefactos y navegación de versiones.

## Hallazgo importante

Aunque existe el código de `experience_sink` en `agent_runtime.py`, la revisión del `do_POST` actual de `server.py` muestra registrada la ruta `/api/agent-graph/plan`, pero no se observa todavía una ruta efectiva `/api/agent-graph/execute` en la tabla de despacho revisada.

Por tanto, **la conexión runtime → servidor que se pretendía cerrar todavía debe verificarse/corregirse antes de considerarla implementada**. No conviene asumir que una ruta existe solamente porque hubo un commit destinado a añadirla.

## Qué falta para cerrar este bloque

1. Conectar realmente el endpoint de ejecución con `AgentRuntime`.
2. Conectar ese runtime con `make_runtime_experience_sink()`.
3. Pasar de extremo a extremo: perfil → selección → plan → ejecución → auditoría → candidato.
4. Probar fallo de persistencia sin invalidar una ejecución correcta.
5. Ejecutar CI completo y corregir cualquier regresión real.
6. Añadir pruebas HTTP de integración, no solamente pruebas que inspeccionen que un texto existe en `server.py`.
7. Verificar que el feedback humano cambia el estado del registro y que solo `accepted` entra en selección futura.
8. Verificar que las referencias seleccionadas llegan efectivamente a cada agente/modelo que debe usarlas.
9. Verificar manifiesto/frescura de artefactos derivados y que los enlaces de descarga apunten a la versión actual.
10. Implementar la navegación UI de versiones; el backend de navegación existe, pero la experiencia visual todavía requiere cierre.
11. Ejecutar una regresión end-to-end real con generación de MD/HTML/DOCX y auditoría.
12. Reducir el riesgo del PR antes de mergearlo: el PR #1 está en estado draft y actualmente contiene 257 commits y 82 archivos modificados.

## Qué ya no falta conceptualmente

La separación fundamental ya está definida:

`perfil objetivo → experiencia aceptada relevante → planificación → ejecución → auditoría → evaluación → candidato → feedback humano → accepted → referencia futura`

Eso evita convertir automáticamente una salida del modelo en conocimiento aprendido.
